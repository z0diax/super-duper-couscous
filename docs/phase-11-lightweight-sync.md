# Phase 11: lightweight revision and reference synchronization

## Scope and protocol

Phase 1–10 reports and the current state, authentication, mutation, and targeted refresh paths were reviewed. The authoritative `app_records` write transaction, `state.php`, `load_state()`, projections, and the default five-second full-state poll remain. Phase 11 adds a reversible cutover for installations with all eight operational targeted-read flags enabled.

Before cutover, AppContext keeps a revision ref from the initial `state.php` GET, successful POST responses, and visible five-second/focus/online whole-state GETs. Each mutation sends that revision to `state.php`. The transaction locks `app_meta` with `SELECT ... FOR UPDATE`, loads state, compares the submitted revision, performs one action, persists records/projections and audit, increments the revision, loads state again, and returns the filtered state. A stale revision returns 409. The old client displays an error and performs a full-state GET. No mutation helper automatically retries. Files are uploaded to `files.php` before the business POST, so a rejected POST previously left unattached upload rows and bytes.

With `VITE_LIGHTWEIGHT_STATE_SYNC=1`, AppContext still does its initial state bootstrap. Its visible five-second and focus/visibility/online checks then use `GET /api/revision.php` instead. The endpoint authenticates the session, selects only `revision,config_revision` from `app_meta`, and returns `{revision,configRevision,user}`. `user` is the authenticated public current-user profile, used to detect role/profile changes. It does not call `load_state()` or return application collections. `bootstrap.php` supplies JSON, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and session authentication. A hidden tab skips timer checks; return to visibility, focus, and online reconnect check promptly. Concurrent checks coalesce. The five-second cadence matches the former revision freshness and is not faster.

The known revision updates immediately from every successful POST. A changed revision from another user does **not** invalidate all mounted resources. Those components own their targeted reads. A 409 refreshes the revision and invalidates only the action's affected resource, then keeps the user's input available for review and resubmission. There is no automatic replay. A failed lightweight endpoint leaves an alert with Retry sync; it never falls back to state.php polling. A request with an uncertain network outcome must be checked against the resource before resubmission.

## Configuration and user freshness

`app_meta.config_revision` is an additive `BIGINT UNSIGNED` column. The installer adds it to an existing database; run `php scripts/install.php` before deploying the new PHP endpoints. The existing state transaction increments it atomically with the global revision when an account or any of `systemRoles`, `assigneeDesignations`, `classifications`, `workflowTemplates`, or `employmentRoutingRules` changes. User management actions update `app_users` directly, so they are explicitly classified as configuration changes. Ordinary operational writes do not advance it.

On a higher configuration version the client fetches `GET /api/reference.php`. That endpoint returns only public users and the five named configuration collections, plus the version and current user; it does not return documents, Payroll, Leave, EWP, audit, or migration data. It reads its bounded collections in a transaction and shares authentication/cache headers with revision.php. The client merges only those references into AppContext. Login/bootstrap and successful local configuration writes also update references from the existing state response. Cross-user reference changes normally appear within five visible seconds or on return to the tab. A configuration endpoint failure shows the sync alert and is retried by the next check; it does not silently substitute old operational state.

Users are managed by administrators and consumed by assignment names, task routing, personnel and intake forms. Roles control capabilities; templates, classifications, designations, and employment rules drive form options and routing. These are low-frequency edits with server-side authorization and validation. A temporarily stale option may cause a rejected save; it cannot grant access. `revision.php` authenticates on every request, so expired sessions, deleted/disabled users, or changed credentials return 401 and clear the client session. It returns the public profile on every success, so profile/role changes update the client without a reference payload. New role definitions and capability changes travel through `config_revision` and `reference.php`.

## Mutation and upload handling

The chosen policy is periodic revision checks plus 409 recovery. Adding a preflight GET to every mutation would add one request and network latency even when the five-second check is current, and the server's locked comparison must remain authoritative. File-bearing operations get an immediate revision preflight **before** upload. If that finds a newer revision, the user reviews and resubmits without uploading. If an upload succeeds but preparation or a known API rejection fails, the client calls `DELETE /api/files.php?id=...` for each newly uploaded ID. The DELETE requires CSRF, the uploading user, and `owner_id IS NULL`; attached files cannot be deleted through it. On a network failure after POST submission, the client does not delete uploaded files or retry: the outcome is uncertain and the operator must inspect the targeted record first. Repeated rejected submissions do not reuse or duplicate uploaded IDs. A crash between upload and cleanup can still leave an unattached file; broader garbage collection belongs to a later file lifecycle project.

| Retry class | Operations | Policy |
| --- | --- | --- |
| A: safe after confirmed non-execution | Read-only revision/reference/targeted GET; DELETE of one's own unattached upload | Repeat directly. |
| B: conditionally retryable | Classification/routing/settings updates, edits, reassign/hold/compliance and similar changes whose target still exists | Refresh exact targeted resource and options, review changed fields, then resubmit. No automatic replay. |
| C: user review required | Registration/create, delete, complete step, approval/disapproval, release, external handoff/return, Payroll processing, file-bearing actions, Leave/EWP transitions | Review current state and outcome before any resubmission. A timeout after POST could have committed, so never blindly repeat. |

The server still serializes writes with the global revision lock. A 409 means the submitted revision did not match; it is not evidence that the intended operation was applied. Business-rule 409s remain possible after the revision matched, so the resource is still refreshed and the user reviews it. Simultaneous writes at the same revision admit one and reject one.

## Rollout, remaining state calls, and freshness

The frontend flag `VITE_LIGHTWEIGHT_STATE_SYNC` defaults to `0`. The Vite build rejects `1` unless Registry, Detail, Tasks, Search, Document Shell, Payroll, Dashboard, and Leave/EWP targeted frontend flags are all `1`. Their matching backend gates must also be enabled before a cutover build is served. Rollback is a rebuild with the lightweight flag `0`; then the legacy five-second state poll resumes. Preserve the new column and endpoints during rollback.

In lightweight mode the five-second routine path does **not** call `load_state()`. Remaining frontend whole-state calls are: (1) one `state.php` GET after login/session restoration, needed for reference data and legacy reporting/configuration/archival views; (2) an explicit database-startup retry; (3) a targeted Document Detail 401 compatibility recovery call; and (4) every successful or rejected business POST to `state.php`, whose legacy mutation path and successful whole-state response remain. Legacy mode additionally has the five-second/focus/online GET and 401/409 recovery GET. Header search and targeted resource APIs do not call state.php. The initial whole-state load is a Phase 12 candidate; it is intentionally retained here.

| Operational surface | Visible-tab refresh in targeted mode | Expected idle cross-user staleness, excluding server/network delay |
| --- | --- | --- |
| Header/Sidebar document and Payroll summaries | 5 seconds, focus/visibility | Up to 5 seconds |
| My Tasks document and Payroll queues | 5 seconds, focus/visibility | Up to 5 seconds |
| Payroll lists, vouchers and open batch detail | 5 seconds, focus/visibility | Up to 5 seconds |
| Registry and open Document Detail | 15 seconds, focus/visibility | Up to 15 seconds |
| Leave list/detail and EWP list | 15 seconds, focus/visibility | Up to 15 seconds |
| Dashboard | 30 seconds, focus/visibility | Up to 30 seconds |
| Header search | On submit | Fresh at next search |

Registry, Document Detail, and document My Tasks gained their own visible/focus cadence because their earlier revision-only effects depended on whole-state polling for cross-user updates. A global revision change alone does not make a fan-out of targeted requests. Targeted API errors remain visible in the owning component with its existing retry; no whole-state fallback is introduced. Audit, archive, migration, and some configuration report views still use bootstrap/local mutation state and can remain stale until reload or local mutation. Their ongoing freshness is a Phase 12 question, not an operational read claim.

## Local fixture measurements

`scripts/benchmark_phase11_sync.mjs` uses a disposable MariaDB fixture with 100/1,000/10,000 each of Documents, Leave, EWP, and audit rows, plus 100/1,000/1,000 Payroll items. HTTP sizes are response body bytes; times are medians of three localhost requests. `tests/phase11-memory-probe.php` runs each read in its own CLI process and reports PHP peak memory allocation, avoiding cross-request high-water contamination. These are local observations, not production latency estimates.

For one visible hour on the EWP screen with Header/Sidebar summaries mounted, the routine synchronization is 720 requests in either mode. The unchanged targeted reads are approximately 1,680 requests (two five-second shell summaries and one 15-second EWP read); entry/focus, mutations, and search add requests in either mode. Thus this scenario is approximately 2,400 requests/hour in both modes, with the same targeted-response bytes in both. The **sync portion alone**, extrapolated from the measured 10,000-row responses, is 14,290,054,560 bytes/hour for legacy state polling versus 277,920 bytes/hour for revision polling. The corresponding sum of isolated median server times is about 7,512,559 ms versus 14,472 ms; these are workload extrapolations, not wall-clock or concurrent throughput predictions. A configuration change adds one ~8.3 KB reference response when noticed. The Phase 10 seven-read active-user bundle measured 109,486 bytes, but that bundle is not an hourly cadence and is not multiplied here. Dashboard adds its own 30-second targeted reads when that view is mounted. The new Registry/Detail/document-task refreshes add their own targeted requests only while those views are mounted.

## Verification and failure behavior

The Phase 11 API fixture exercises two users, Document and Payroll writes after revision sync, stale Payroll 409 recovery, versioned references, user role/deletion and 401, cache headers, simultaneous writes, and uploader-only cleanup. The two-context browser test exercises a cross-user Registry and EWP update, a post-sync EWP write, a stale write with the revision endpoint unavailable, form preservation, focus recovery, and uniqueness of the resubmitted record. It counts one state.php GET for B: the initial bootstrap. Existing targeted suites and integration tests provide the other operational parity checks. Failure behavior is explicit: revision/reference unavailable or offline shows the sync alert and retains the known revision; reconnect/focus retries; 401 ends the client session; a targeted API failure stays in that component; 409 refreshes revision and affected resource without replay; two concurrent writes cannot both commit at the same revision. If a network timeout obscures a POST result, the operator checks the record before another submission.

The browser configurations were built separately: all flags off (legacy Registry and failed-save smoke passed); all eight targeted flags on with lightweight off (Registry, Detail, Payroll, Dashboard/Leave/EWP, Search/Shell and Tasks targeted checks passed with matching backend gates); and all eight targeted flags on with lightweight on (Phase 10 operational and Phase 11 two-context/conflict/configuration-reconnect checks passed). In an initial targeted legacy sweep, Search and Tasks fixtures had the Payroll frontend flag on but the backend gate off. Matching the fixture gate resolved Search failures; one Tasks login intermittently returned a CSRF error, then the exact test passed in isolation. It is test debt to monitor, not evidence that targeted resource data was wrong. Older broad-suite stale labels and fixed-date assertions remain as classified in Phase 10.

Phase 2–11 API tests passed 16/16. The integration suite remains **24/26**: its two administrator-override expectations still expect denial where current server policy permits an administrator. Document and Payroll projection `--verify` checks reported zero issues. TypeScript lint, syntax checks of seven touched PHP files, and all three production build configurations passed. A deliberately incompatible lightweight-on/all-targeted-off build was rejected with the required flag list. The workspace build artifact was restored to the default-off configuration after verification.

## Phase 12 recommendation

After observing the cutover in use, consider replacing the initial whole-state bootstrap and reporting/configuration readers with bounded endpoints, and consider an upload-expiry maintenance path. Measure production concurrency and remaining report freshness before removing state.php or its compatibility mode. Phase 12 is not implemented here.
